section: Security

- **A key in a committed `vendor/`, `build/` or `coverage/` folder is found again.** The secret scan skipped folders named build, dist, coverage, reports and vendor at any depth, so a live key in `src/vendor/` or `app/api/build/route.ts` gave a clean report. Below the repo root those names now get every rule. At the root they get the fixed-shape rules (key prefixes, private keys); `.env`, `*.env` and `*.env.*` files and shell scripts (`.sh`, `.bash`, `.zsh`) there get every rule, and a root folder git ignores is still skipped. `.bash` and `.zsh` files are now read everywhere. The coverage ledger and the brief say which root folders got only those rules.
- **Code and `.env` files in a translation folder get every secret rule.** Only `.json`, `.yml`, `.yaml`, `.properties` and `.po` files in `locales/`, `i18n/`, `lang/` and similar folders run just the fixed-shape rules now. Before, a password in `lang/.env` or `i18n/db.ts` was missed.
- **A short fallback secret is masked.** `secret: process.env.SESSION_SECRET || 'kq7Zp9'` showed the last 4 characters of the fallback in reports. The quoted value is now masked on its own, by the same rule as other values: `***` under 20 characters.
- **Line numbers no longer cost quadratic time.** Each secret hit counted lines from the start of the file, about 19 s of CPU on a hostile 2 MB bundle in the live check. The line index is built once per file.
- **The `@anthropic-ai/` exemption needs proof.** A package was exempt from "writes AI agent config" and "invokes an AI CLI" when the lockfile's `name` said `@anthropic-ai/…`, which anyone writing the lockfile controls. Now the lock path, the name in the installed `package.json` and a `registry.npmjs.org` or `registry.yarnpkg.com` tarball URL must all name the same `@anthropic-ai/` package. A package from a private mirror keeps its finding.
- **`--baseline -q` reports a finding that escalated.** A finding whose severity rose above the baseline's (a low that became critical) counted as unchanged and exited 0. It now counts as new, and so does a secret finding with more lines or a new value, or a sink finding with a new call. A `--repo` report keeps a short salted hash of each fixed-format secret value, such as a provider key or a private key (`valueTags`, salt in `secretTagSalt`), never the value, so a key swapped for another counts as new even when its masked form looks the same. Passwords and other `name = value` secrets get no hash, because a person may have chosen the value and the salt is in the report; those, and a baseline without hashes, compare the count and the first masked value. A baseline written before 2.3.2 can show secrets as new once, because short values are masked differently: write a fresh one after the upgrade.
- **A suppression stops at a severity.** Suppressions in memory and `penthera.suppress.json` take a severity (`--severity`, `"severity"`), and stop applying when the finding is more severe. An entry without one covers up to medium. Suppressions written before 2.3.2 for a high or critical finding no longer hide it, and the pre-commit hook blocks on it again: add `"severity"` to keep them.
- **`--giants` keeps the higher severity.** When a tool's finding folded into one of Penthera's, Penthera's severity won, so a tool's critical behind Penthera's medium exited 0. The fold now keeps the higher one. Merging the results of several scans keeps the more severe of two duplicates too.
