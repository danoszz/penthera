section: Security

- **A dependency file Penthera can't read fails `penthera deps` with exit 2, and the rest is still checked.** A lockfile or requirements file that is a FIFO, a device, a link out of the project or over the 64 MiB cap is not read. It is an info finding, `File not read: <file>`, the other inputs are still scanned, and the run is incomplete: it exits 2, and the brief says why. A refused `-r` include (`-r /dev/null`, say) skips only the include, so the other pins in that file are still checked. An unreadable input never passes CI as an empty tree. `penthera install` stops when it can't read the proposed lockfile. The JSON report has a new `incomplete` field that lists each file, and the MCP `check_dependencies` brief has `exit_code` 2. In the GitHub Action the job fails even with `fail-on: none`, after the PR comment (which says `Incomplete:` and names the file) and the SARIF upload. Vercel Security Review found two ways an earlier 2.3.2 build exited 0 here.
- **A secret hash no longer covers a password that looks like a key.** In an earlier 2.3.2 build, a password with `sk-` and 20 letters or digits inside a longer word matched the OpenAI legacy key rule, so the report held a hash of it (`valueTags`) and its salt. A fixed-format match now gets a hash only when it is a whole token (nothing but a space, a quote, `=`, `:` or `,` beside it), outside every `name = value` rule's match and outside the `user:password@` part of a URL. The legacy `sk-` OpenAI shape never gets one. Each of them is still reported, and a baseline compares it by count and masked value. Found by our fact-check.
